# 新建项目 Harness 工程化规则

## 使用方法（先读这一节）

**这份文档是什么**：一份**自包含**的规则文档。它把"智能体优先（Agent-First）"项目的建设标准全部写在本文里——**执行时不需要访问任何外部链接，也不需要原始资料**。你（或你的 AI）照着做即可。

**本文档的定位是「施工图」，不是永久文件。** 施工期常驻在仓库里；竣工后按 **§16** 拆解归档——**不能中途删掉，也不能永远原样留着**。原因与操作见 §16。

> **本文参考了 OpenAI 官网的最佳实践文献《Harness engineering: leveraging Codex in an agent-first world》（中译《工程技术：在智能体优先的世界中利用 Codex》，2026-02-11）。** 该文献的全部可操作要点已内联到本文，无需另行查阅或访问原文。

**注意：本文只管"怎么建"，不管"建什么"。** 项目需求必须由你提供——这一点见下面第 2 步，**跳不过去**。

**怎么用（五步）**

1. **放进仓库**：把本文档复制到目标仓库的 `docs/HARNESS-RULES.md`（或仓库根 `HARNESS-RULES.md`）。它是项目的第一份文件，也是智能体每次会话的入口规范之一。
2. **同时准备你的项目需求**：新建项目的仓库是空的，AI **无法从代码里看出你要做什么**。所以你必须同时告诉 AI 这个项目是什么。两种办法任选：

   - **附需求文档**：把 PRD / 需求说明 / 原型说明放进仓库（如 `docs/requirements.md`），让 AI 一并阅读；
   - **提示词简述**：直接在提示词里写清**项目目标、主要功能、目标用户、目标平台形态**，以及已知的技术偏好或团队约束。

   **需求说得越具体，AI 越不需要反问。** 什么信息都不给就让它建项目，等于让它替你做产品决策——而那条路一定会跑偏。

3. **让 AI 读规则 + 读需求 + 开工**：新开会话，说下面这句话（可直接复制）：

   > 阅读仓库内的 `docs/HARNESS-RULES.md`，并阅读我提供的项目需求（`docs/requirements.md`，或我在本次对话中说明的需求）。
   > 严格按规则体系从 Day 0 搭建这个项目。
   > **第一步先处理我的需求**（规则 §3.2）：先把需求复述给我确认，再提取技术栈；如果**语言或框架不明确，必须通过交互向我确认，不要自己假设**。
   > 技术栈定下来后，再做 **§3.3 框架确认**；若确认为 Tauri，**必须按 §3.4 逐条向我提问**（是否生成 GitHub CI / 目标平台多选 / Release 直接发布还是出 draft），**问完再动手**。
   > 在需求澄清与技术栈确认完成之前，不要开始写业务代码，也不要生成 `.github/workflows/` 下的任何文件。

4. **按 §13 的检查清单逐阶段验收**：阶段 A–F 每个勾完再进入下一个。
5. **收官拆解**（最后一阶段完成后）：按 **§16** 把本文档拆开——一次性流程移入 `docs/exec-plans/completed/` 存档，长效契约抽进 `AGENTS.md` / `core-beliefs.md` / `ARCHITECTURE.md` 常驻。**本文档不是永久常驻文件，但阶段没走完之前不要删、不要精简。**

**你（人类）在这套流程里的角色**：不写代码行。你负责四件事——**提供需求与确认技术栈、回答决策问题、验收结果、确认收官拆解**。所有代码、配置、文档、CI 由智能体产出。

**本文档与其他文档的关系**：姊妹文档是《存量项目 Harness 工程化规则》（`turn-project-to-harness-rules.md`），用于把**已有代码库**改造为 harness 工程化。**新建项目用本文档，改造存量项目用那一份，不要混用。**

**版本**：v1.0 ｜ **适用范围**：所有智能体优先的新建项目 ｜ **总纲**：**人类掌舵，智能体执行。**

## 0. 核心心法（先立观念，再立规矩）

| 心法 | 含义 | 对新建项目的直接要求 |
|---|---|---|
| **不手写代码** | 代码由智能体产出，人类不直接贡献代码行 | 项目从第一次提交起，所有文件（含规范本身）都由智能体生成 |
| **约束即倍增器** | 一旦编码成规则，就立刻作用于所有地方 | 项目第一天就要有 linter / 结构测试 / CI 门禁 |
| **看不到 = 不存在** | 智能体运行时无法访问的内容，对它来说就是不存在 | 知识必须进仓库（代码化、版本化），不能只活在聊天记录或人脑里 |
| **给地图，不给说明书** | 上下文是稀缺资源，超长指令会挤掉真正重要的信息 | `AGENTS.md` 约 100 行，只做目录，不做百科 |
| **纠错便宜，等待昂贵** | 高吞吐环境下，快速修正优于严格阻塞 | 采用短生命周期 PR + 弱阻塞门（前提是反馈回路已建成） |
| **债务是高息贷款** | 技术债要小额高频偿还，不能攒着一次性还 | 建立定期"垃圾回收"式重构任务 |

**角色重定义**：工程师的工作重点从"写代码"转向 **系统、架构和杠杆作用**。

当进展不顺时，标准答案不再是"再努力一点"，而是追问：

> **究竟还需要什么样的能力，我们又该如何让这个能力对智能体来说既清晰可读、又可强制执行？**

## 1. 项目启动规范（Day 0）

### 1.1 起点

**起点是需求，不是代码。** 空的 Git 仓库里没有任何信息能告诉 AI"要做什么"，所以第一件事永远是**把需求讲清楚**（见 §3.2）。

- **前提（第 0 项）**：用户已提供项目需求（需求文档，或提示词里的口头描述）。**需求不明时不得开工。**
- **技术栈**：由需求推出；语言或框架不明时**必须交互确认**，不得自行假设（见 §3.2）。
- 从**一个空的 Git 仓库**开始。不做"先手工搭好再说"的过渡态。
- 首次提交即建立完整骨架：**仓库结构、CI 配置、格式化规则、包管理器设置、应用框架**。
- 初始 `AGENTS.md` 也由智能体编写。

### 1.2 Day 0 必须交付的 10 项

0. **需求澄清结论 + 技术栈结论**（目标平台形态 / 语言 / 框架 / 包管理器 / 构建方式；见 §3.2，**交互确认后落盘**）
1. `.gitignore` + 格式化规则 + 提交规范（由智能体生成）
2. 包管理器与依赖锁定策略
3. 应用框架与目录骨架
4. `AGENTS.md`（≤ 100 行，作为内容目录）
5. `ARCHITECTURE.md`（领域与包分层的顶层地图）
6. `docs/` 目录结构（记录系统的载体）
7. 自定义 linter + 结构测试的**第一批规则**（哪怕只有 3 条）
8. CI 流水线骨架（lint / test / build 三件套先跑通）
9. **框架确认 + 条件式 GitHub CI 决策**（见 §3，**Tauri 项目必须交互确认，不得自行假设**）

> **第 0 项排在最前，是因为后面每一项都依赖它。** 需求不清 → 技术栈无法定 → 骨架无从搭 → §3 的框架确认没有输入。
>
> 第 9 项是新项目最容易漏的一环：Tauri 项目如果没有在 Day 0 确定打包发布链路，第一个 tag 打下去就会卡住，或者到 Windows CI 才发现图标、产物路径、草稿态一堆问题。见 §3 与 §12。

### 1.3 工作方式

- 采用**深度优先**：把大目标拆成小构建块（设计 / 代码 / 评审 / 测试），提示智能体造出这些块，再用它们解锁更复杂的任务。
- 人类几乎完全通过提示与系统交互：描述任务 → 运行智能体 → 允许其开 PR。
- **不要人工搬运上下文**（不要"复制粘贴到 CLI"）。智能体应直接使用标准开发工具（`gh`、本地脚本、仓库内嵌技能）自行采集上下文。

## 2. 仓库结构与知识存储规范

### 2.1 标准布局

```text
AGENTS.md                  # 地图（<=100 行），被注入上下文
ARCHITECTURE.md            # 架构顶层地图
docs/
├── design-docs/           # 设计文档，已编目+索引，含验证状态
│   ├── index.md
│   ├── core-beliefs.md    # 智能体优先的操作原则（核心理念）
│   └── ...
├── exec-plans/            # 执行计划，一等公民
│   ├── active/            # 活跃计划（含进度与决策日志，提交入库）
│   ├── completed/         # 已完成计划
│   └── tech-debt-tracker.md
├── generated/             # 自动生成的知识（如 db-schema.md）
│   └── db-schema.md
├── product-specs/         # 产品规格，按领域切分
│   ├── index.md
│   └── ...
├── references/            # 外部依赖的 llms.txt 等参考
│   └── ...
├── CI.md                  # CI 配置决定（见 §3，必须建）
├── requirements.md        # 项目需求（由用户提供，§3.2 的输入，必建）
├── DESIGN.md              # 设计规范
├── FRONTEND.md            # 前端规范
├── PLANS.md               # 计划规范
├── PRODUCT_SENSE.md       # 产品判断力
├── QUALITY_SCORE.md       # 质量评分：按领域/架构层打分并追踪差距
├── RELIABILITY.md         # 可靠性要求
└── SECURITY.md            # 安全要求
```

### 2.2 四条硬规则

- **知识必须版本化入库。** 存储在 Google Docs / 聊天记录 / 人脑里的知识，智能体访问不到，等于不存在。
- **计划是一等工件。** 小改动用临时轻量计划；复杂工作写入 `exec-plans/`，附带进度与决策日志并提交入库。活跃计划、已完成计划、已知技术债全部集中存放且版本受控，使智能体无需外部上下文即可运行。
- **决策必须落盘。** 任何交互式确认（尤其 §3 的三个 CI 问题）的结果，都要写进仓库文档。**只在对话里确认过、仓库里没有记录的决策，等于没做。**
- **文档要能被机械校验。** 专职 linter 与 CI 作业验证：更新状况、交叉链接、结构正确性。另设定期 `doc-gardening` 智能体，扫描与真实代码行为不符的过时文档并发起修复 PR。

### 2.3 绝对禁止：巨型 `AGENTS.md`

把 `AGENTS.md` 当百科全书的做法必然失败，四个原因：

| 问题 | 后果 |
|---|---|
| 上下文是稀缺资源 | 巨大指令文件挤掉任务、代码与相关文档，智能体要么错过关键约束，要么优化错误的约束 |
| 过多指导反而无效 | 当一切都"重要"，就什么都不重要；智能体退化为本地模式匹配，而非有意识导航 |
| 它会立即腐烂 | 变成陈旧规则的坟场，智能体无法判断哪些仍有效，一旦停止维护就成为吸引人的麻烦源头 |
| 难以核实 | 单个 blob 无法做机械检查（覆盖率、新鲜度、所有权、交叉链接），漂移不可避免 |

## 3. 需求澄清、技术栈确认与条件式 GitHub CI 配置

> **本节是强制流程，不是可选项。**
> **执行顺序**：**F0 需求澄清 → 技术栈**（§3.2）→ **F1 确认框架**（§3.3）→ **F2 Tauri 三问**（§3.4），或 **F3 跳过**（§3.5）。
> **前置**：用户必须先提供项目需求（见「使用方法」第 2 步）。没有需求就没有技术栈，没有技术栈这一节无从执行。

### 3.1 为什么必须先确定框架

CI 配置的形态**完全由框架决定**：

- **Tauri**（桌面应用）：需要多操作系统 matrix 构建、Rust 交叉编译 target、平台专属打包格式、Release 资产上传。
- **其他类型**（纯 Web / Node 服务 / CLI / 库 / 移动端 / 数据脚本）：`lint + test + build` 三件套即可，**不需要**多平台打包与 Release 流水线。

强行为非桌面项目生成桌面 CI，会带来：CI 永远红、无用文件污染仓库、后续维护者不敢删。

### 3.2 步骤 F0：先处理用户需求，把技术栈定下来〔新建项目专有〕

**为什么这一步必须在最前面**：新建项目的仓库是**空的**——没有 `package.json`、没有 `src-tauri/`、没有一行源码。**任何"扫描文件来判断框架"的方法，在空仓库上必然失效。** 所以新建项目的框架不是"判定"出来的，而是**从用户需求里确认**出来的。

**若用户没有提供需求**：**立即停下并向用户索取**（需求文档，或提示词里的口头描述）。不允许在需求不明的情况下自行编一个项目来做——那等于替用户做产品决策。

**子步骤**

1. **读取需求**：读用户放在仓库里的需求文档（如 `docs/requirements.md`），或读提示词里描述的需求。
2. **复述并确认**：把理解到的需求用几句话复述给用户，请其确认。**理解偏差在这个环节修正，成本最低。**
3. **从需求中提取技术栈结论**，分三种情况处理：
   - **需求已明确语言与框架**（如"做一个 Tauri 桌面应用"）→ 直接采用，记为结论。
   - **需求提到产品形态但未指定框架**（如"做一个桌面工具""做一个本地小软件"）→ 进入第 4 步交互确认。
   - **需求完全没提技术栈** → 进入第 4 步交互确认。
4. **交互确认技术栈**（语言或框架不明时**必须问，不得自己假设**）：
   - 先给出**基于需求的推荐方案 + 理由**（1–2 个候选，说清各自取舍），再请用户选择；
   - 需要问清的：**目标平台形态**（桌面 / Web / 移动 / CLI / 服务端 / 库）、**语言与框架**、**包管理器**、以及是否已有技术偏好或团队约束；
   - 不要只问"你想用什么技术"，要给可选项并说明代价。
5. **产出技术栈结论**：至少包含 **目标平台形态 / 语言 / 框架 / 包管理器 / 构建方式**五项。
6. **落盘**：写入 `docs/design-docs/core-beliefs.md` 与执行计划的技术栈节。**只在对话里确认过、仓库里没有的技术栈结论，等于不存在。**

**验收标准**

- [ ] 需求已被读取，且已向用户复述确认过一遍。
- [ ] 技术栈结论五项齐全，且**每一条都能回溯到"用户的需求"或"用户的确认"，没有一条是 AI 自行假设的**。
- [ ] 若发生过交互确认，确认过程与结论已落盘。
- [ ] 若用户确实没有提供需求，本轮已明确向用户索取（而非跳过）。

### 3.3 步骤 F1：确认项目框架

**注意：新建项目不要用文件扫描来判定框架。** 空仓库里既没有 `package.json` 也没有 `src-tauri/`，扫描必然扫不到任何东西——**必须改为读取 §3.2 得出的技术栈结论**。

| 判定结果 | 判定依据 |
|---|---|
| **Tauri** | §3.2 的技术栈结论中，框架明确为 Tauri（典型搭配：Rust + `src-tauri/` + 前端框架） |
| **其他** | §3.2 的技术栈结论中，框架不是 Tauri（Web / Node 服务 / CLI / 库 / 移动端…） |

**输出要求**：把判定结果与依据（技术栈结论原文 + 用户确认记录）写进仓库文档（`docs/CI.md`，模板见 **附录 D**）。**不允许只在对话里说一句"这是 Tauri 项目"。**

### 3.4 步骤 F2：判定为 Tauri → 强制三步交互询问

**必须逐个提问，必须等用户回答后再继续。** 三个问题不得合并，不得替用户默认。

---


**问 1｜是否为该项目生成 GitHub CI 配置（`.github/workflows/`）？**

- **「是」** → 继续问 2、问 3。
- **「否」** → **跳过本节剩余全部内容**。在仓库文档中记录"用户于 `YYYY-MM-DD` 明确放弃 GitHub CI 配置"。**后续任何阶段不得静默补建。** 基础门禁（lint / test / build）仍按 §13 阶段 A、B 建立，只是不生成打包发布流水线。

---

**问 2（仅当问 1 = 是）｜CI build 需要产出哪些目标平台？〔多选〕**

- `windows`
- `mac`
- `ubuntu`

> 说明：可多选，也可只选一个。用户选几个就只配几个，**不要"顺便都加上"**。

---

**问 3（仅当问 1 = 是）｜CI build 完成后，Release 如何发布？**

- **直接正式发布**：CI 构建完立即作为正式 Release 上线，访客可下载。
- **先出草稿（draft）**：CI 只创建草稿 Release 并上传资产，由用户自己在 GitHub 网页上检查后手动点发布。

> 补充说明（供你在回答前判断）：`mac` 在 CI 上分两种 CPU 架构（arm64 / x86_64），默认两者都构建；若只想出一份可另行说明。

---

**交互硬性约束**

- 用户未回答完三个问题之前，**不得生成任何 `.github/workflows/` 文件**。
- 不得把三个问题合并成一次多选，不得给出"我建议默认全都要"之类的预设答案后直接动手。
- 用户只选部分平台时，matrix 只保留所选平台。
- 用户回答"否"之后，仍需在 `docs/CI.md` 记录该决定与日期。

**询问结果必须落盘。** 写入 `docs/CI.md`，模板见 **附录 D**。

### 3.5 步骤 F3：判定为其他类型 → 明确跳过

若 §3.3 判定为"其他"：

- **跳过整个 GitHub CI 小节**：不问 §3.4 的三个问题，不生成 `.github/workflows/` 的打包发布流水线。
- **基础门禁照建**：lint / test / build 三件套仍按 §13 阶段 A、B 落地。
- **照样记一条**：在 `docs/CI.md` 写下"框架判定 = 其他类型，本项不适用多平台打包与 Release 流水线"。

### 3.6 三个回答如何落到 CI 配置

| 用户回答 | 落点 |
|---|---|
| **平台选择** | `release.yml` 的 matrix 只保留所选 OS 的构建行 |
| **直接发布** | `tauri-action` 设 `releaseDraft: false`；guard job 不追加草稿转正兜底 |
| **先出 draft** | `tauri-action` 设 `releaseDraft: true`，由用户手动发布；guard 的 `--draft=false` 兜底**必须去掉** |

> 具体 YAML 模板与实战坑清单见 **§12 Tauri 工程附加规范**。

## 4. 渐进式披露（Progressive Disclosure）

- 智能体从**一个小而稳定的切入点**开始，被明确指引"下一步该去哪里看"。
- 而不是一开始就被海量信息淹没。
- 落地方式：`AGENTS.md`（入口）→ `ARCHITECTURE.md` / `docs/index.md`（一级目录）→ 具体领域文档（详情）。

**验收标准**：一个新来的智能体，仅凭仓库内容，能否在不追加人工提示的情况下找到它需要的一切？

## 5. 架构规范（硬约束）

### 5.1 分层与依赖方向

每个业务域划分为固定的一组层，**依赖只能单向"向前"**：

```text
Types → Config → Repo → Service → Runtime → UI
```

- **依赖方向严格验证，仅允许有限的一组边。** 其他任何依赖都不被允许。
- **横切关注点**（认证、连接器、遥测、功能标志）只能通过**单一显式接口 `Providers`** 进入。
- 这些约束通过**自定义 linter（同样由智能体生成）+ 结构测试**机械强制。

> 这种架构在传统团队里通常要等到数百名工程师时才考虑。**对编码智能体来说，它是早期先决条件**——有了约束，速度才不会下降，架构才不会漂移。

### 5.2 强制执行不变量，而非微观管理实现

- 例：**要求在边界处解析数据形状（parse, don't validate）**，但**不规定具体实现方式**（模型偏好 Zod，但规范不指定库）。
- 明确区分"哪里必须限制"和"哪里不需要限制"：**中央层面强制边界，本地层面允许自主权**。
- 重视界限、正确性、可重复性；在边界之内，允许实现表达有极大自由。

### 5.3 智能体友好性优先于人类风格偏好

- 生成代码不总符合人类风格偏好，**这没关系**。只要输出正确、可维护、对未来的智能体运行清晰可读，即算达标。
- 人类品味持续反馈进系统：审查评论、重构 PR、面向用户的 Bug，都要**记录为文档更新，或直接编码进工具**。
- **当文档不够完善时，把规则转化为代码。**

## 6. 品味不变式（Golden Principles）

> 定义：**带有主观意见的机械规则**，用于保持代码库可读性和一致性，以便未来运行的智能体。
> 特点：编码进仓库后，**人类的品味一旦被捕捉，就会持续应用于每一行代码**。

### 6.1 必选清单

| 编号 | 不变量 | 机械检查方式 |
|---|---|---|
| T1 | **文件大小限制** | 行数/字节数阈值，超限即失败 |
| T2 | **结构化日志**（禁止字符串拼接日志） | 静态强制 |
| T3 | **模式与类型的命名约定** | 正则校验命名模式 |
| T4 | **边界处解析数据形状** | 禁止直接读取未校验的外部结构 |
| T5 | **禁止"YOLO 式"探测数据** | 未通过类型/Schema 校验的字段访问即失败 |
| T6 | **优先使用共享工具包**，而非手写 helper | 检测重复实现 |
| T7 | **依赖方向与允许的边** | 结构测试扫描 import 图 |
| T8 | **特定平台的可靠性要求** | 检查超时、重试、优雅退出等必需模式 |
| T9 | **文档必填节与交叉链接** | 文档 lint |
| T10 | **覆盖率下限** | 覆盖率报告比对 |

### 6.2 关键实施细节

**自定义 lint 的错误信息中，要注入修复指令。** 这样智能体读到报错就知道怎么改，形成自纠正闭环。

### 6.3 为什么这些规则在智能体时代是"倍增器"

在以人为本的工作流中，这些规则可能显得迂腐或束缚；但有了智能体，**一旦编码，就能立即应用于所有地方**。

## 7. 会话纪律（通用硬性要求）

> 以下三条适用于**所有项目**的每一次智能体会话，不区分技术栈；写入 `AGENTS.md` 承载为铁律。

### 7.1 版本一致性

- 前端、后端、根端各自的版本声明**必须始终一致**；任何一次版本变更同步更新所有声明点。
- Tauri 工程的三个声明点：`package.json` / `src-tauri/tauri.conf.json` / `src-tauri/Cargo.toml`。
- 用**脚本一次 bump 多处**（如 `scripts/_bump_version.py`），禁止手工散改其中一处。
- tag 发布时 CI guard 机械校验 `tag == package.json` 版本，不一致直接 fail——版本漂移在源头拦截。

### 7.2 提交颗粒度：单一职责

- 一个改动会话内的提交按**单一职责原则**拆分：一次提交只做一件事（一个功能 / 一次修复 / 一次重构 / 一次文档更新）。
- Commit message 使用 Conventional Commits 前缀（`feat:` `fix:` `chore:` `docs:` `refactor:` `test:`…），body 详细说明动机、方案、影响面。
- 进行中的半成品按进度分次提交；普通提交不受测试与门禁阻塞。
- **会话结束前的最后一次提交必须通过全部本地门禁**，并在 message 注明 `[已测试]` / `[未测试]`。

### 7.3 用户提示词记录（`prompr-history.txt`）

- 仓库根维护一个 `prompr-history.txt`，**只给用户自己看**：
  - 加入 `.gitignore`，**不 push 到远程**；
  - 仓库内不放置任何"读取此文件"的要求或引用——智能体只追加，不读取、不合并。
- 每轮对话中，把用户提示词**结构化后追加到文件末尾**（纯 append，不读取已有内容做合并整理）：
  - 记录头：日期时间、模型名、agent 名字（运行环境取不到就省略该字段）；
  - 正文：按要点拆条记录提示词（保留原始语义与关键措辞，不改写意图）；
  - 每条记录末尾追加一行分隔线 `------`。
- **过滤规则**：提示词少于 10 个字的不记录（寒暄、单字确认类噪声）。
- 格式示例：

```text
[2026-10-02 11:17 CST] model=GLM-5.3-Flash | agent=ZCode
- 要求：对前后端与根端版本一致做要求
- 要求：改动的代码以单一职责为颗粒度多次提交
------
```

## 8. 可读性与可观测性规范

### 8.1 目标：让智能体能从仓库直接推理出完整业务域

- 应用应能**根据 git worktree 启动**，使智能体可为每次变更启动并驱动一个实例。
- 接入 **Chrome DevTools 协议**，并提供处理 DOM 快照、屏幕截图、导航的**技能**。
  → 使智能体能够复现错误、验证修复、直接推理 UI 行为。**Tauri 项目同样适用**：WebView 侧可走 DevTools 通道，Rust 侧靠日志与指标。
- 日志、指标、追踪通过**本地可观测性堆栈**暴露给智能体；该堆栈对每个工作树是**临时的**，任务完成后连同日志指标一并删除。
- 智能体可用 **LogQL 查日志、PromQL 查指标**。

### 8.2 可验证的性能断言

有了上述上下文，这类提示才可行：

- "确保服务启动在 800ms 内完成"（Tauri 项目可断言窗口首帧时间）
- "这四个关键用户旅程中的任何 span 都不得超过两秒"

### 8.3 依赖与抽象的选择偏好

- **倾向可完全内化于仓库中推理的依赖和抽象。**
- 对智能体而言，通常被称为"枯燥"的技术，因**可组合性、API 稳定性、在训练集中的表现**，反而更容易建模。
- 某些情况下，**让智能体重新实现部分功能子集，比绕过公共库中不透明的上游行为更便宜**。
  - 参考案例：不引入通用 `p-limit` 风格包，而是自研带并发的 map 辅助函数——与 OpenTelemetry 仪表紧密集成、100% 测试覆盖率、行为完全符合运行时预期。

> 把系统的更多部分转化为**智能体可检查、可验证、可直接修改**的形式，直接提高杠杆效应。

## 9. 反馈回路与自主闭环规范

### 9.1 标准 PR 循环

1. 人类描述任务，运行智能体，允许其打开 PR
2. 智能体**本地自审**自己的变更
3. 智能体在本地和云端**请求额外的、特定用途的智能体审查**
4. 智能体**响应所有人工或智能体的反馈**
5. 循环往复，直到所有智能体审查者满意

> 人类可以审 PR，但**并非必须**。随着时间推移，应把几乎所有审查工作调整为**智能体对智能体**。

### 9.2 端到端自主能力（成熟度目标）

给定一个提示，智能体应能：

- [ ] 验证代码库的当前状态
- [ ] 重现已报告的漏洞
- [ ] 录制演示故障的视频
- [ ] 实施修复措施
- [ ] 通过运行应用验证修复
- [ ] 录制第二个视频，演示解决方案
- [ ] 打开 Pull Request
- [ ] 回应智能体和人类反馈
- [ ] 检测并修复构建故障
- [ ] 仅在需要判断时才交由人工处理
- [ ] 合并更改

> ⚠️ 此行为**高度依赖仓库自身的结构与工具投入**，不应假定可以泛化——至少目前还不行。

### 9.3 人类介入的正确姿势

人类始终参与，但抽象层次不同：**排定优先级、把用户反馈转化为验收标准、验证结果。**

当智能体遇到困难时，把它视为一个**信号**：识别缺失的东西——工具、指导、约束、文档——并将其反馈到仓库中，**且始终由智能体自己编写修复**。

## 10. 合并与质量策略规范

### 10.1 原则

> **纠错成本低，而等待成本高。**

### 10.2 具体做法

- **PR 生命周期要短。** 允许高频提交。
- 仓库运行时**尽量减少阻塞合并门**：只拦真正危险的东西（编译失败、测试大面积失败、架构违规）。
- 测试偶发失败（flaky）通常通过**后续重跑**解决，而不是无限期阻碍进展。

### 10.3 适用前提（重要）

在低吞吐量环境中，弱阻塞门是不负责任的选择；只有当你**已经在测试、验证、审查、反馈处理、恢复上做了充分投入**，弱化门禁才是正确选择。

## 11. 熵管理与垃圾回收规范

**问题**：完全自主的智能体会**复现仓库中已存在的模式——包括那些不均衡或不够理想的模式**，随时间推移不可避免地导致漂移。（早期做法是每周五花 20% 时间人工清理"AI 残渣"，**不可扩展**。）

### 11.1 解决方案：把"黄金原则"编码进仓库 + 建立循环清理流程

- 定期运行一组**后台智能体任务**：
  1. 扫描偏差（偏离黄金原则之处）
  2. 更新质量等级（`QUALITY_SCORE.md`）
  3. 发起**有针对性的重构 PR**
- 其中大多数 PR 应做到**一分钟内可审查并自动合并**。

### 11.2 心智模型

> 其功能类似于**垃圾回收**。技术债就像一笔高息贷款：不断以小额贷款方式偿还，总比让债务累积后痛苦地一次性解决要好得多。

### 11.3 目标节奏

**每天**发现并解决不良模式，而不是让它们在代码库中传播数天或数周。

## 12. Tauri 工程附加规范

> **仅当 §3.3 判定为 Tauri、且 §3.4 问 1 回答"是"时适用。**
> 下面每一条都来自真实发布链路的实战验证，照抄已验证结构，不要从零写。

### 12.1 tag 触发的多平台自动 Release

**workflow 固定结构**

1. **guard job**：校验 tag 版本与 `package.json` 一致；预建 Release（已存在则跳过，保留手写说明）。
2. **publish matrix（`fail-fast: false`）**：`macos-latest` × 2（aarch64 / x86_64，用 `--target` 分开构建）、`windows-latest`、`ubuntu-22.04`——**不要 `ubuntu-latest`**（Tauri 的 Linux 依赖按 22.04 包名安装）。**按 §3.4 问 2 的实际勾选裁剪 matrix，不要全部照抄。**
3. 每个 job 统一步骤：checkout → pnpm/action-setup → setup-node（cache pnpm）→ rust-toolchain（含 targets）→ `pnpm install --frozen-lockfile` → `tauri build` → 分平台上传。

**实战坑清单**（每条都真实翻过车）

- `bundle.targets` 必须为 `"all"`；写死 `["app"]` 会导致多平台 CI 只有 macOS 出包。
- **Windows 构建必需 `src-tauri/icons/icon.ico`** 并加入 `bundle.icon` 声明——macOS 本地构建碰不到该路径，首台 Windows CI 才暴露；用 `tauri icon <源图>` 生成，附带产物（Square* / Android / iOS 等）不入库。
- macOS 专属 API（`title_bar_style` 等）必须 `#[cfg(target_os = "macos")]` 隔离，否则 Windows 编译失败、Linux 直接报错；前端平台判断用 `userAgent` 而非编译期。
- 上传产物用 `find target -path '*/release/bundle/*'` 通配——带 `--target` 时产物在 `target/<triple>/release/bundle`，不带时在 `target/release/bundle`，两种都要覆盖；排除 deb 的 `control.tar.gz` / `data.tar.gz` 中间产物。
- 构建失败把日志尾部写成 `::error::` check-run 注解——无仓库管理员权限时 API 下载原始日志 403，注解是无认证可读的唯一排障通道。
- guard 预建 Release 后追加 `gh release edit --draft=false` 兜底：**删除旧 tag 重打会把已发布 Release 打回草稿**（对访客与匿名 API 不可见，而 `gh release view` 对草稿判定"已存在"而跳过创建，草稿将永远是草稿）。
  ⚠️ **若 §3.4 问 3 用户选择"先出 draft"，此项兜底必须去掉**，否则会违背用户意图自动转正。
- 无 updater 配置时的完整资产 = 7 个：双 dmg + msi + setup.exe + deb / rpm / AppImage；`.app.tar.gz` / `.sig` 只在开启 updater 时产出。
- Verify（push 触发）建议双 job：frontend（ubuntu，前端检查 + 构建）+ native（macOS，原生测试 + 全套门禁）——**有 Rust 代码务必保留 macOS 原生测试 job**；tag 推送不跑 Verify，避免与 Release 双重编译。

### 12.2 构建目录与产物

- cargo 构建目录定位到**仓库根 `target/`**：`src-tauri/.cargo/config.toml` 设 `[build] target-dir = "../target"`。
- **注意 cargo 配置按 CWD 向上发现**：`cargo --manifest-path src-tauri/...` 从仓库根运行时读不到该配置，产物会落回 `src-tauri/target`；脚本内显式 `export CARGO_TARGET_DIR="$PWD/target"` 兜底。
- build 完成自动清理**可再生的临时产物**（`dist/`、`target/release/bundle/`）；**对下次构建有帮助的编译缓存一律保留**（`target/release`、`target/debug`），保证增量编译秒级完成。
- 本地 build 的 `.app` 产物**以版本号命名放在 `target/` 根**（如 `AppName_0.1.26.app`），只保留最新一份。

### 12.3 `package.json` 脚本（根）

- `build`：只在本地 build 出 app 产物（不打 dmg、不发布）。
- `release`：push 代码到远程，并对远程做 tag 动作——**先删除远程旧同名 tag，再打新 tag**（幂等重发）。
- 联动约束：正因 release 会删 tag 重打，CI guard 的草稿态兜底是**必需项而非可选项**（见 12.1），**除非**用户在 §3.4 问 3 明确选择了"先出 draft"。

## 14. 反模式清单（禁止事项）

| 反模式 | 为什么禁止 | 正确做法 |
|---|---|---|
| **需求不明就开工** | 没有需求 AI 只能替你编产品决策，方向必错 | 先索取需求并复述确认（§3.2） |
| **靠扫描文件判定新建项目的框架** | 空仓库扫不出任何东西，判定必然失效 | 从需求推出技术栈，再读技术栈结论（§3.2 → §3.3） |
| **语言/框架不明却自行假设** | 技术栈是不可从代码推断的用户决策 | 交互确认后再动手（§3.2） |
| **不问用户就给 Tauri 项目生成 CI** | 平台范围与发布方式是不可推断的产品决策，猜错等于白做 | 严格走 §3.4 三问 |
| **给非桌面项目配多平台打包流水线** | CI 永远红，污染仓库 | §3.5 明确跳过 |
| **交互确认过但仓库没记录** | "看不到 = 不存在"，下次会话决策丢失 | 写入 `docs/CI.md` |
| **用户选了 draft，却在 guard 里加自动转正兜底** | 直接违背用户意图，草稿被静默发布 | §12.1：选了 draft 就去掉该兜底 |
| 写一个 1000 行的巨型 `AGENTS.md` | 挤占上下文、立即腐烂、无法机械校验 | `AGENTS.md` 只做目录，≤100 行 |
| 把知识留在 Slack / Google Docs / 人脑 | 智能体访问不到，等于不存在 | 全部推入仓库并版本化 |
| 手工搭好骨架再交给智能体 | 骨架结构不由智能体塑造，后续难以自洽演进 | 从空仓库开始，骨架由智能体生成 |
| 人工复制粘贴上下文进 CLI | 消耗人类最稀缺的注意力 | 让智能体直接用 `gh`、脚本、仓库内技能采集 |
| 用文档描述规则，却不写成代码 | 文档会腐烂，且无法强制 | 文档不够好时，把规则转化为代码 |
| 引入行为不透明的重依赖 | 智能体无法在仓库内推理其行为 | 优先"枯燥"、可组合、API 稳定的技术；必要时自研子集 |
| 允许"YOLO 式"数据探测 | 智能体会基于猜测的结构继续构建 | 验证边界，或使用类型化 SDK |
| 在低吞吐/无反馈回路时弱化门禁 | 无纠错能力却放开阻塞，等于放任腐化 | 先建反馈回路，再谈弱化门禁 |
| 靠人类每周集中清理"AI 残渣" | 不可扩展，债务累积成高息贷款 | 定时后台扫描 + 小额高频偿还 |
| 对生成代码的"人类风格"吹毛求疵 | 浪费人类注意力，收益极低 | 只要求：正确、可维护、对未来智能体清晰可读 |
| `bundle.targets` 写死 `["app"]` | 多平台 CI 只有 macOS 出包，缺 Win/Linux 安装包 | 设为 `"all"`（见 12.1） |
| 到 Windows CI 才发现缺 `icon.ico` | tauri-build 生成 Windows 资源文件必需，macOS 本地构建碰不到该路径 | Day 0 用 `tauri icon` 生成并加入 `bundle.icon`（见 12.1） |
| 删 tag 重打后 Release"消失" | 已发布 Release 被打回草稿，对访客不可见且 guard 不再重建 | guard 加 `gh release edit --draft=false` 幂等兜底（**用户选了 draft 时不要加**，见 12.1） |
| 以为 `--manifest-path` 会加载 crate 内 cargo 配置 | cargo 配置按 CWD 向上发现，产物落错目录、CI 缓存失效 | 脚本显式 `export CARGO_TARGET_DIR`（见 12.2） |
| 用 `ubuntu-latest` 构建 Tauri | Linux 依赖按 22.04 包名安装，新版本环境缺包 | 固定 `ubuntu-22.04`（见 12.1） |
| 手工散改多个版本声明点 | 版本漂移，tag 发布时 guard 失败 | 脚本一次 bump 全部声明点（见 7.1） |
| **规则文档在项目里永久原样常驻** | 780 行僵尸文件，与 §2.3"塞满等于没有"直接冲突，且必然与现状漂移 | 竣工后按 §16.3 拆解归档 |
| **阶段没走完就删掉规则文档** | 智能体后续会话失去入口规范，规范退化成口口相传 | 只有阶段 G 的自检通过后才归档（§16.6） |
| **把唯一的规则母本随项目一起删掉** | 模板资产丢失，下个项目从零重写、重踩旧坑 | 母本与仓库副本分开管理（§16.5） |

## 16. 本文档的生命周期与收官处置

> **一句话结论**：本文档是**施工图**——开工前读、施工中查、**竣工后拆解归档**。既不是用完即弃的临时文件，也不是永久常驻的百科。拆出来的两半必须分开处理：**一次性流程归档留痕，长效契约抽出常驻。**

### 16.1 三个阶段分别怎么处置

| 阶段 | 本文档在哪 | 谁读 | 动作 |
|---|---|---|---|
| **① 施工期**（Day 0 起，至阶段 A–F 全部勾完） | `docs/HARNESS-RULES.md`，**全文** | 你 + 智能体（**每次新会话都必须先读**） | **不删、不精简、不就地改写。** 它此刻是项目的入口规范之一 |
| **② 竣工时**（最后一次施工会话） | 同上 | 智能体执行拆解，你确认 | 按 §16.3 逐项拆解：一次性部分归档，长效契约迁移。**拆解单独一次提交** |
| **③ 竣工后**（常态开发） | 降级为 `docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`，历史留痕、不再被常规加载 | 只在追溯"当初为什么这么定"时读 | 常驻入口改为 `AGENTS.md` + `core-beliefs.md` + `ARCHITECTURE.md` |

### 16.2 为什么"用完就删"和"永远留着"两头都不对

**不能删，三个理由**：

1. **决策依据会一起消失**。为什么这样分层、为什么只 build 这三个平台、为什么发布走 draft——答案都在这份文档里。删掉之后，接手的人只能重新猜，而猜出来的方案大概率和现状不一致。
2. **反模式清单和核心信条是长效资产**，不是施工期专属。
3. **很容易连母本一起删掉**（见 §16.5），那损失的不是一个项目，是模板资产本身。

**不能原样留，三个理由**：

1. **和本文档自己的信条直接冲突**。§2.3 明令"绝对不能有巨型 `AGENTS.md`"，理由是"塞满等于没有"。一份近 900 行的 `HARNESS-RULES.md` 常驻在 `docs/` 里，就是同一个病。
2. **一定会漂移**。项目真跑起来之后，实际做法会与文档逐渐分叉。没人维护的文档就是**僵尸文件**——而僵尸文件比没有文件更糟，它会让智能体照着错的规则干活。
3. **`docs/` 里每个常驻文件都是智能体的上下文成本**。§4 渐进式披露的前提是"入口足够小，深层内容按需下推"。

### 16.3 拆解映射表（竣工时逐项执行）

| 本文档的内容 | 去向 | 理由 |
|---|---|---|
| Day 0 清单、阶段 A–F 验收标准、§3.2–§3.5 步骤与访谈脚本 | **归档** → `docs/exec-plans/completed/harness-<YYYY-MM-DD>.md` | 决定已经做完了，答案已物化进目录结构、配置文件与 CI |
| §3.4 三问的回答记录 | **已在** `docs/CI.md`（§3.4 强制落盘） | 结论要能随时查，过程才归档 |
| §5 分层与依赖方向 | **常驻** → `ARCHITECTURE.md` + 结构测试 | 每天在用，且必须机械可执行 |
| §6 品味不变式 / 黄金原则 | **常驻** → linter 规则 + 结构测试；"为什么"进 `core-beliefs.md` | 能被工具执行的，不要靠文档提醒 |
| §7 会话纪律（版本一致性、单一提交职责、提示词记录） | **常驻** → `AGENTS.md` 的硬性约束 + 提交门禁脚本 | 每会话都要遵守，且部分可机器校验 |
| §12 Tauri 附加规范 | **常驻** → `docs/CI.md` | 发布链路是长期资产 |
| §14 反模式清单 | **常驻** → `core-beliefs.md`（精简为 top 5） | 长效，但不必全文照搬 |
| §15 度量指标 | **常驻** → 项目看板 / `docs/metrics.md` | 长期运营对象，与施工无关 |
| 附录 E 术语表 | 并入 `core-beliefs.md`；术语少则直接删 | 按需 |
| 开头的文献出处备注 | **跟着 `core-beliefs.md` 走** | 方法论来历应可追溯 |
| 「使用方法」一节 | 删 | 只服务于施工期 |
| 本文档（§16 本身） | 归档 | 它也是施工期内容 |

### 16.4 判据：一条规则该留还是该删

只问一句话：**它是"用来做决定的"，还是"用来约束日常的"？**

- **用来做决定的**（要不要 CI / build 哪些平台 / 正式发还是出 draft / 建哪些文档 / 分几批）→ 决定做完了，答案已经**物化**在 `.github/workflows/`、`docs/CI.md`、目录结构里，文档里那份就成了重复信息。**归档。**
- **用来约束日常的**（不许跨层依赖 / 单文件不超 N 行 / 不许手写重复逻辑）→ 天天都要用。**常驻，而且要以机器可检查的形式常驻。**

更强的判据：**能写成 linter 规则或结构测试的，文档里就不要重复写。** 文档只留"为什么"（进 `core-beliefs.md`），"怎么做"交给工具——这正是 §6.2「强制执行不变量，而非微观管理实现」的落地。

### 16.5 一个容易搞混的区分：母本 vs 副本

|  | **母本** | **仓库副本** |
|---|---|---|
| 是什么 | 本文档的**模板原件**，放在你的个人规则库／模板仓库里，**不在业务仓库** | 复制进每个目标仓库的 `docs/HARNESS-RULES.md` |
| 生命周期 | **永久保留**，而且**每做完一个项目就回来迭代一次** | 按 §16.3 竣工归档 |
| 为什么 | 每做一次都会踩到新坑（"空仓库判不出框架""CI 草稿态陷阱"就是这么踩出来的），这些经验要回流母本，下个项目才不重踩 | 它服务的是这一个项目 |

**如果没有独立的模板仓库**：在业务仓库里把母本保留为 `docs/templates/HARNESS-RULES.md`，并在归档副本头部留一条指针指向它。**不要因为"用过一次"就把唯一的母本当垃圾扔了。**

### 16.6 收官动作（阶段 G）

阶段 A–F 全部勾完后，在**同一次会话**里完成：

1. 按 §16.3 逐项拆解，产出 `docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`。
2. **自检**：把本文档从仓库里拿掉，智能体仅凭 `AGENTS.md` + `core-beliefs.md` + `ARCHITECTURE.md` 是否仍能遵守**全部硬约束**？答"否"说明还有东西没迁移，回到第 1 步。
3. `git mv docs/HARNESS-RULES.md docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`（用 `git mv` 保留历史）。
4. 归档文件开头加一行：`> 一次性施工图，已竣工归档。常驻规范见 AGENTS.md / core-beliefs.md / ARCHITECTURE.md。`
5. **单独一次提交**，如 `docs: 归档 harness 施工图，长效契约已迁移至常驻文档`。
6. **母本回流**：本次施工若发现本文档有缺口或错误，同步修正母本（§16.5）。

> **不要做的事**：第 2 步没通过就把本文档删掉。**文档退休的前提是它的职能已被工具和常驻文档接管**——没被接管的规则一旦删掉，就退化成口口相传。

## 附录 E：术语表

| 术语 | 含义 |
|---|---|
| **harness** | 支撑结构。指围绕代码库的一整套环境、约束、工具与反馈回路 |
| **harness 工程化** | 把工程工作重心从写代码转向设计环境、明确意图、构建反馈回路 |
| **不变量（invariant）** | 必须始终成立、可被机械检查的约束 |
| **品味不变量** | 主观但可机械执行的一致性规则（命名、日志、文件大小等） |
| **记录系统（system of record）** | 唯一的真实信息来源。本项目指仓库内的版本化纯文本工件 |
| **渐进式披露** | 从短小稳定的入口开始，逐层引导到更深细节 |
| **结构测试** | 用测试方式校验架构约束（依赖方向、允许的边），而非校验运行时行为 |
| **文档园丁（doc-gardening）** | 定期扫描陈旧文档并提交修复 PR 的自动化任务 |
| **执行计划（exec plan）** | 复杂工作的正式计划工件，含进度与决策日志，随代码一起版本化 |
| **地图 vs 百科** | 入口文件是目录（地图）；深层真相在各自文档里（百科） |
| **YOLO 式探测** | 不校验结构就直接访问数据字段，凭猜测构建逻辑 |
| **门禁（gate）** | 提交/合并前必须通过的自动化校验 |
| **matrix** | GitHub Actions 的多任务并行策略，按平台/架构展开 |
| **guard job** | Release 流程里的前置校验任务：核对 tag 与版本声明一致，并预建 Release |
| **draft（草稿 Release）** | CI 上传好资产但不对访客公开的 Release，需人在 GitHub 上手动点发布 |

## 结语

> 构建软件仍然需要纪律，但**纪律更多地体现在支撑结构上，而不是代码上**。保持代码库一致性的工具、抽象和反馈回路，变得越发重要。

**当前最棘手的挑战**集中在：设计环境、反馈回路和控制系统——帮助智能体实现"大规模构建和维护复杂、可靠的软件"这一目标。
